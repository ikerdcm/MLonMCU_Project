1 · Repository structure

The DS-CNN work lives in cnn-trad-fpool3_model/, which has three clean top-level parts: the model artifacts, the training pipeline, and the per-platform deployments.

Every platform folder follows the same pattern, which is the nice part:

  • a vendor project (the actual firmware) — often two variants: a 32-bit/float baseline and an optimized 8-bit/INT8 version, so you can show the optimization delta;
  • tools/ — measurement driver (kws_measure_*.py), JSON configs, and run_{offline,live}_measurement.sh;
  • measurements/ — captured runs as summary.json + *.csv.

Context: the repo root also holds a second model family (ai85kws20netv3_model/), a top-level Experiments/ results store with its own schema, plus Papers/ and the project brief. Those are outside your DS-CNN scope but explain why measurement results appear in more than one place (see §6).

2 · The model — DS-CNN-L

Architecture

  • Depthwise-Separable CNN, defined in keras_model.py → 'ds_cnn_l'
  • 64 filters · 6 DS blocks (the reference ds_cnn is 4 blocks)
  • Conv(10×4, s2) + BN + ReLU → 6×[ DW-Conv(3×3) + BN + ReLU + Conv(1×1) + BN + ReLU ] → AvgPool → Dense(12)
  • The first 4 blocks share shapes with the MLCommons kws_ref_model, so finetune.py warm-starts from it.

I/O & size

  • Input: [1, 49, 10, 1] — 49 time frames × 10 MFCC bins (1 s @ 16 kHz, 30/20 ms window/stride)
  • Output: 12 classes — down, go, left, no, off, on, right, stop, up, yes, silence, unknown
  • Compute: 3,937,717 MACs / inference
  • INT8 weights: ~35–48 KB (STM32 reports weights=34.7 KB, activations=18.3 KB)

⚠️ The Coral README claims "~460 KB params (INT8)" — that looks like a typo (off by 10×); the real INT8 model is ~35–48 KB. Worth correcting when you touch that file.

5 · Is each board "maxed out"?

Your assumption was that the non-Coral boards are already at their max. That's half right — here's the honest per-board verdict and the actual levers (matches the optimization table you have):

MAX78000 — effectively maxed

0.16 ms is set by the fixed CNN-accelerator pipeline, not by code you can tune. INT4 isn't supported on the path used; compiler -O3 only touches wrapper code; even a smaller model barely changes accelerator timing. No meaningful optimization remains — leave it. (Only theoretical lever: clock/voltage scaling for energy, not latency.)

STM32U5 — NOT maxed; the biggest opportunity

This is a CPU/CMSIS-NN workload, so software changes move the needle a lot. From 224 ms (float) it's already at 64 ms (INT8). Remaining levers: INT4 weight compression (X-CUBE-AI --compression 4bit, ~2× fewer memory reads), latency-optimized codegen, compiler -Os/-O3, and a smaller model (4 blocks / 32 filters). Realistic target ≈ 20–30 ms. If the project cares about absolute latency/energy, this is where the hours pay off — but it's outside your Coral focus.

Coral — nearly maxed for latency, but real wins elsewhere

All 12 ops already map to the Edge TPU (0 CPU fallback), and 1.8 ms is tiny. Edge TPU is INT8-only (no INT4), and host-side compiler flags don't help. So the only latency lever is a smaller model → ~1.2 ms (−33%). BUT the more valuable Coral work is accuracy (fix calibration), reproducibility, and energy measurement — see §7.

7 · Coral deep-dive & improvement opportunities

Ranked by value ÷ effort. The first two are nearly free and the most defensible "improvements" you can show.

1

Re-quantize with REAL calibration data low effort · accuracy win

convert_static_int8.py falls back to random Gaussian calibration unless you pass --data_dir. Random calibration picks poor INT8 ranges → avoidable accuracy loss on the deployed Edge-TPU model. Re-run with the real Speech Commands set, then re-compile:

python3 scripts/convert_static_int8.py --data_dir ~/data/speech_commands_v002
./scripts/compile_edgetpu.sh ../../models/ds_cnn_l_static.tflite

Measure accuracy before/after with eval_quantized_model.py. Zero architecture change, pure quality gain.

2

Make the Coral pipeline reproducible correctness

Mismatch to resolve: convert_static_int8.py reads trained_models/kws_ref_model — that's the 4-block reference (~2.6M MACs) — but the deployed ds_cnn_l_static_edgetpu.tflite measures 3.94M MACs (6-block DS-CNN-L). So the script in the repo does not reproduce the shipped model. Pin the script to the actual 6-block SavedModel (or document which checkpoint was really used) so anyone can regenerate the Coral model from scratch.

3

Measure Coral power/energy fills a gap

Energy/inference is the project's main cross-board comparison metric, and Coral's summary.json is the only one with no energy_estimate. Capture board power during the bench run so Coral is comparable to MAX78000 (23 µJ) and STM32U5 (4,610 µJ) on the same axis. Likely your single highest-value deliverable for "improving Coral".

4

Smaller model → ~1.2 ms higher effort · the latency lever

Train/finetune a 4-block (or 32-filter) DS-CNN, quantize with real data, recompile for Edge TPU (fewer ops → less TPU time). Expect ~1.8 ms → ~1.2 ms and lower energy, at a small accuracy cost. Reality check: 1.8 ms is already invisible next to the 1 s audio window — so frame this as an energy/headroom win, not user-perceived latency.

5

Tune the live path (MFCC + stride) live UX

In apps/kws_live/kws_live.cc the Edge TPU inference (~1.8 ms) is dwarfed by the CPU MFCC compute and the 500 ms inference stride. The firmware already prints mfcc=… us infer=… us — use that to decide whether to shorten the stride or move MFCC tables to OCRAM (both _ocram and _sdram table variants already exist). This improves responsiveness, which is what's actually felt in the live demo.
